## 一、项目概述

**立刻游**是一个本地生活出行 Agent，用户用自然语言描述需求，系统自动生成 Top-3 可执行出行方案（含真实 POI、路线、时间线、预算）。

### 核心价值主张
- 输入：自然语言（"今晚 7 点在上海静安寺，4 个朋友，预算 800 元"）
- 输出：3 套可执行方案，每套含完整时间线、真实地点、路线距离、预算估算
- 执行：一键确认后自动完成购票/订座/配送/分享

## 三、核心流程（POST /api/plans）

```
用户输入
    │
    ▼
[1] IntentParserAgent
    ├── 调用 MiMo LLM 解析意图（超时 15s）
    ├── 提取：location / time_window / group / budget / scenario / poiSearchStrategy
    └── 失败时 fallback 到关键词规则解析

    │
    ▼
[2] ClarificationService.buildClarification()
    ├── 检查 2 个必填字段：location（可定位地点）、timeWindow.start（明确时间）
    ├── 其余字段（duration/group/budget/preferences）自动填充默认值：
    │     duration = 180 分钟
    │     group = {total: 2, type: "friends"}
    │     budget = 500 元
    │     vibe = "轻松出行"
    └── 若有缺失 → 返回澄清卡片，流程终止

    │（字段完整时继续）
    ▼
[3] 并行执行（3路）
    ├── AmapWeatherTool     → 查询城市天气（超时 10s）
    ├── SearchVerifierAgent → Tavily 搜索近期活动口碑（超时 10s）
    └── AmapPoiSearchTool   → 并行搜索 POI（见下方详述）

    │
    ▼
[4] AmapPoiSearchTool（并行搜索）
    ├── 4 路并行（CompletableFuture.allOf）：
    │     ENTERTAINMENT 关键词 × 2
    │     CULTURE 关键词 × 2
    │     DINING 关键词 × 2
    │     EXTRA 关键词 × 2
    ├── 每路搜索：offset=15，半径=8000m，取前 10 条
    ├── 去重后总候选 ≥ 9 条才继续（否则报错）
    └── 限速：Semaphore(3) 令牌桶，200ms 补充一个令牌（≈5 QPS）

    │
    ▼
[5] PlanningService.buildOptions()
    ├── 按距离过滤（锚点 12km 内）
    ├── 排除用户指定的 POI
    ├── 按评分+场景排序候选
    ├── 最多尝试 8 次组合（贪心枚举）：
    │     每套方案：activity + restaurant + extra（3-5 站）
    │     检查：POI 类型覆盖（餐饮+活动）、直线距离预筛（10.5km）、去重
    │     调用 AmapRouteEstimateTool 计算真实路线
    │     检查：路线总距离 ≤ 8km、时间窗口匹配（±tolerance）
    └── 生成 1-3 套方案

    │
    ▼
[6] AmapRouteEstimateTool（并行路线计算）
    ├── 单套方案内各路线段并行计算（CompletableFuture.allOf）
    ├── 使用骑行 API（/v3/direction/bicycling），更符合城市出行实际
    ├── 精度修复：先累加秒数，最后统一除以 60
    ├── 返回：travelMinutes / distanceKm / segmentMinutes（分段时间列表）
    └── segment 缓存：相同起终点复用，避免重复请求

    │
    ▼
[7] PlanValidationService
    └── 校验所有 POI 名称来自高德真实结果（纯本地校验）

    │
    ▼
[8] 方案排序 & 输出
    ├── 归一化评分（0-100）：
    │     评分项（0-40）= avg_rating / 5.0 × 40
    │     时长匹配项（0-20）= max(0, 100 - |duration - totalMinutes|) / 5
    │     距离项（0-40）= max(0, 1 - distanceKm / 8) × 40
    ├── 排序后赋值 name/tagline（避免排序前错位）
    └── 返回 Top-3 方案

    │
    ▼
[9] 用户确认（POST /api/plans/{id}/confirm）
    ├── MockTools.book()     → 模拟购票/订座
    ├── MockTools.delivery() → 模拟配送安排
    └── MockTools.share()    → 生成分享消息（从 timeline 读取实际出发时间）
```

## 四、官方约束满足情况

| 约束条件 | 要求 | 当前状态 | 说明 |
|---------|------|---------|------|
| 路线生成时间 | < 10 秒 | ✅ 满足 | 并行 POI 搜索 ~1-2s + 并行路线计算 ~1-3s |
| 方案生成时间 | ≤ 30 秒 | ✅ 满足 | 总流程 8-15 秒（含 LLM 5-15s） |

| 异常处理 | ≥ 3 类故障 | ✅ 满足 | 无座/无票/路线过远/POI 不足/API 失败 |

## 五、本次重构修复清单

### P0 级修复（根本性逻辑错误）

#### 1. 时间线计算修复（PlanningService）
- **修复前**：每站固定 `index × 95` 分钟间隔，完全忽略实际停留时长
- **修复后**：累加前序站点实际 `durationMinutes` + 路段骑行时间（来自 `segmentMinutes`）
- **影响**：时间线从根本上正确，用户看到的出发/到达时间真实可信

#### 2. fitsDuration 增加下限检查（PlanningService）
- **修复前**：只检查 `totalMinutes ≤ duration + tolerance`，90 分钟方案可通过"4小时"约束
- **修复后**：同时检查 `totalMinutes ≥ duration - tolerance`，方案时长必须在合理范围内
- **影响**：避免生成严重偏短的方案

#### 3. 方案名称排序后错位修复（PlanningService）
- **修复前**：`name/tagline` 在排序前按旧 rank 赋值，排序后 rank 更新但 name 不变
- **修复后**：排序后统一赋值 `rank + name + tagline`，三者始终一致
- **影响**：rank=1 的方案名称一定是"稳妥轻松方案"

#### 4. 评分量纲归一化（PlanningService）
- **修复前**：评分项最大 100，距离项最大 12，权重严重失衡
- **修复后**：评分(0-40) + 时长匹配(0-20) + 距离(0-40)，总分 0-100
- **影响**：方案排序更合理，距离近的方案有实质性优势

### P1 级修复（实用性问题）

#### 5. 澄清机制宽松化（ClarificationService）
- **修复前**：6 个字段全部必填，几乎每次都触发澄清
- **修复后**：只有 `location` 和 `timeWindow.start` 必须澄清，其余自动填充默认值
  - duration 默认 180 分钟
  - group 默认 2 人 friends
  - budget 默认 500 元
  - vibe 默认"轻松出行"
- **影响**：大多数完整输入直接生成方案，无需澄清

#### 6. POI 候选池扩大（AmapPoiSearchTool）
- **修复前**：每关键词取 5 条，搜索半径 5000m，阈值 6 条
- **修复后**：每关键词取 10 条，搜索半径 8000m，阈值 9 条
- **影响**：候选池更充足，3 套不重复方案生成成功率更高

#### 7. 路线 API 改为骑行（AmapRouteEstimateTool）
- **修复前**：步行 API，3km 路程估算 36 分钟，严重高估
- **修复后**：骑行 API（`/v3/direction/bicycling`），3km 约 12 分钟，更符合城市出行实际
- **影响**：路线时间更准确，`fitsDuration` 通过率更高，可行方案更多

#### 8. 路线时间精度修复（AmapRouteEstimateTool）
- **修复前**：逐段整除累加（89s/60=1，3段=3min，实际应为4min）
- **修复后**：先累加总秒数，最后统一除以 60
- **影响**：时间线计算更精确

#### 9. segmentMinutes 返回值（AmapRouteEstimateTool）
- **新增**：`route()` 返回值增加 `segmentMinutes: List<Integer>`
- **影响**：PlanningService 可以准确计算每站开始时间

### P2 级修复（性能/质量问题）

#### 10. MimoClient 注入共享 HttpClient
- **修复前**：每次 LLM 调用新建 HttpClient，无连接池
- **修复后**：注入 `@Qualifier("llmHttpClient")` 单例 Bean
- **影响**：减少 TCP 握手开销，LLM 调用更稳定

#### 11. MockTools 时间修复
- **修复前**：share 消息硬编码"下午14:00出发"，与实际方案时间无关
- **修复后**：从 `timeline[0].time` 读取实际出发时间
- **影响**：分享消息时间与方案一致

#### 12. MockTools book() null 检查
- **修复前**：`timeline` 为 null 时抛 NullPointerException
- **修复后**：null 检查，返回空订单列表
- **影响**：异常情况不再崩溃

### P3 级修复（工程质量）

#### 13. PromptCatalog 启动时缓存
- **修复前**：每次请求读 7 个文件但只用 keySet，白读文件内容
- **修复后**：`@PostConstruct` 启动时加载一次，后续请求直接返回缓存
- **影响**：减少每次请求的磁盘 I/O

## 六、已知局限与后续建议

### 当前局限

1. **LLM 意图解析不稳定**：MiMo API 响应时间 5-15 秒，且解析质量依赖 prompt 设计。若 LLM 解析失败，fallback 到关键词规则，可能丢失用户意图细节。

2. **骑行 API 不适用所有场景**：骑行路线假设用户骑自行车，对于步行景区内部或驾车跨区场景不准确。更好的方案是根据距离动态选择交通方式（<1km 步行，1-5km 骑行，>5km 驾车）。

3. **POI 候选池仍可能不足**：在小城市或偏僻区域，高德 POI 数据稀疏，即使扩大半径也可能不足 9 条，导致方案生成失败。建议增加降级策略：扩大半径 → 降低评分门槛 → 减少方案数量。

4. **时间线不考虑营业时间**：当前不验证 POI 在用户指定时间段是否营业，可能推荐已关门的地点。

5. **无流式输出**：后端同步等待所有步骤完成才返回，用户等待期间无进度反馈（前端有模拟进度条，但后端无实时推送）。

6. **澄清后仍可能触发二次澄清**：若用户在澄清时回答"西湖附近"（无城市名），`isConcreteLocation` 仍返回 false，可能再次触发澄清。

### 后续优化建议

| 优先级 | 建议 | 预期收益 |
|--------|------|---------|
| 高 | 增加 SSE 流式输出，实时推送规划进度 | 用户感知延迟降低 60% |
| 高 | 动态选择交通方式（步行/骑行/驾车） | 路线时间更准确 |
| 高 | POI 不足时自动扩大半径降级 | 小城市成功率提升 |
| 中 | 验证 POI 营业时间 | 方案可行性提升 |
| 中 | 地理聚合优化（K-Means 分区） | 减少无效跨区移动 |
| 低 | 用户历史偏好学习 | 个性化推荐 |
